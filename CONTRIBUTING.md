# Contributing to Sentence Transformers

Contributions are welcome, including bug reports, fixes, documentation, examples, and help with existing issues and pull requests.

## Contribution guidelines

AI assistance is welcome. These expectations apply to all contributors, whether or not they use AI tools.

1. **Own the contribution.** Read every changed line, understand why the approach is correct, and be prepared to explain it during review. You are responsible for the code, documentation, and messages you submit, including anything generated by an AI tool.

2. **Demonstrate why the problem matters.** For bug reports and fixes, include a minimal, runnable reproducer and a realistic affected workflow. Describe the expected and actual behavior, relevant package versions, and any error traceback. Say whether you encountered the problem in actual use or discovered it through code analysis. For features, explain the use case and how the change helps users.

3. **Check for existing work.** Search open and recently closed issues and pull requests before submitting. If similar work exists, link to it and explain what your contribution adds. Avoid opening duplicate reports or competing fixes without a meaningful difference.

4. **Submit work that is ready for review.** Resolve known failures, remove unnecessary changes, and verify your claims before requesting review. Run the tests relevant to your changes and include regression coverage for bug fixes. Include the test commands you ran and their results in the PR description, along with any checks you could not run. Performance claims should include measurements before and after the change. Review should focus on assessing the contribution, with the author handling its preparation.

5. **Disclose significant AI assistance.** If AI generated a substantial part of your code or text, briefly describe what it helped with in the PR description. Routine autocomplete does not need disclosure. Include any unresolved uncertainty or limitations that reviewers should know about.

6. **Keep submissions focused and concise.** Explain the problem, the change, and the evidence needed to review it. Review and edit AI-generated descriptions, comments, and replies before posting. Avoid unrelated refactoring, speculative cleanups, and repeated submissions for individual instances of the same pattern. Group related mechanical fixes into a clear, reviewable scope.

7. **Preserve backwards compatibility.** Existing models, pretrained weights, and public functions should produce the same outputs unless the change is fixing a real bug.

8. **Fix the cause, not the symptom.** Explain the underlying cause and why your change addresses it, following existing patterns where possible. If the problem originates in a dependency such as [Transformers](https://github.com/huggingface/transformers) or [huggingface_hub](https://github.com/huggingface/huggingface_hub), report it upstream and link the issue or fix in your contribution. Explain why any workaround in Sentence Transformers is necessary.

Maintainer review time is limited. We may close submissions that are unverified, duplicative, out of scope, or disproportionately costly to review. Repeated low-effort submissions may result in restrictions on further contributions.

You may use your own PR description format as long as it includes the relevant description, validation, and AI disclosure information.

## Documentation

Update documentation, docstrings, or examples when useful, especially for new features and changes to user-facing behavior. Keep code snippets runnable and consistent with the implementation.

The documentation at [SBERT.net](https://www.sbert.net/) is built with Sphinx. Source pages live in [`docs/`](docs/) and use reStructuredText (`.rst`) or Markdown (`.md`, parsed with MyST). Follow the format and conventions of the file you are editing. Markdown pages can embed reStructuredText directives in an `eval-rst` fenced block.

API reference pages use Sphinx autodoc to render Python docstrings. Follow the existing Google-style docstrings, including sections such as `Args`, `Returns`, and `Example`. Application and training examples live in [`examples/`](examples/). Add new documentation pages to the appropriate Sphinx toctree in [`index.rst`](index.rst) or the relevant section index. Edit source files rather than generated HTML.

In a virtual environment with an editable Sentence Transformers installation (see [Development setup](#development-setup)), install the documentation dependencies and build a local preview from the repository root:

```bash
uv pip install --group docs
make docs
```

Open `docs/_build/index.html` to inspect the result.

## Development setup

After cloning the repo (or a fork) to your machine, in a virtual environment, run:

```bash
python -m pip install -e ".[dev]"

pre-commit install
```

To check code quality, run:

```bash
pre-commit run --all-files
```

To test your changes, run the relevant tests by passing their paths to `pytest`. To run the default test suite:

```bash
pytest
```
